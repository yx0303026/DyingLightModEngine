# 联机玩家名称显示逆向记录

## 分析目标

目标是把本地客户端显示的玩家名称替换为按阵营编号的名称：

- 人类：队友 1、队友 2、队友 3……
- 猎手：猎手 1、猎手 2……

名称替换应只影响本机的显示，不改写 EOS 属性、网络复制状态或玩家真实账号名。

## 已确认的证据

### 玩家条目中的名称节点

`0x18079DFC0`（IDA 名称 `sub_18079DFC0`）查找玩家条目中的 `T_PlayerName`，并将其转换为 `IUIText`，保存到条目对象中。该函数属于玩家条目初始化路径，不负责联网身份采集。

### 玩家名称条目更新路径

`0x18079E320`（IDA 名称 `sub_18079E320`）接收玩家对象并执行以下操作：

- 通过 `IGSObject::GetNetOwnerID` 取得玩家的网络所有者 ID。
- 经全局游戏对象的虚表调用，以该 ID 获取对应玩家/条目。
- 更新玩家条目组件，并访问名称相关的 UI 节点。
- 构造 `_NAME&` 本地化键并更新名称相关显示内容。

因此这是已定位的玩家显示更新路径之一，也是继续追踪“玩家对象名如何写入 UI 文本”的首要函数。当前静态证据尚不足以证明它覆盖所有显示位置，也没有确认最终文本写入的唯一公共函数。

### 玩家列表与猎手专用 HUD

- `HUD_PLAYERS_LIST`、`HUD_PLAYERS_INDICATOR`、`HUD_HUNTER_INFO` 在 `0x1811241A0` 的 HUD 组件注册表中注册。`0x1811241A0` 是组件名到 HUD 类型的映射，不是名称替换函数。
- `0x1808030F0` 引用了 `L_HunterPlayers`，属于猎手玩家列表 UI 路径。它与通用玩家条目路径不同，应单独核对该列表项文本如何更新。
- `T_PlayerName` 的多处引用涉及不同 UI 条目；仅修改一个初始化函数不能保证已有条目和其他 UI 同步刷新。

### 大厅元数据不是 HUD 显示名

模组现有 `EngineLobbyCollector` 通过 EOS 读取 `NAME_s`、`TEAM_l`、`ZOMBIE_b` 和 `PLAYER_ID_s`，再保存到 `EngineLobbyData`。这些字段用于大厅成员快照；当前代码没有把它们接入游戏自身的 HUD 玩家文本。

现有 `DlModLobbyMemberV1` 也没有游戏内 `NetOwnerID` 字段。因此不能仅凭 EOS PUID/SteamID 假设它与 `0x18079E320` 使用的网络玩家 ID 可直接对应。

## 推荐实现方式

采用本地客户端显示名映射，不发送或修改网络数据：

1. 在已确认的玩家实体/网络会话层取得每个活动玩家的稳定身份键，并确认它能覆盖 `NetOwnerID` 生命周期。
2. 根据游戏的实际阵营状态分类，再在每个阵营内分配序号。猎手与人类分别计数；玩家离开、重连或转阵营时更新映射。
3. 在 IDA 中继续追踪 `0x18079E320` 使用的对象访问和 `_NAME&` 更新链，确认原始名称的读取函数及最终 UI 写入调用。优先在玩家 UI 名称消费点替换，不拦截全局 `IUIText::SetText`。
4. 对 `HUD_PLAYERS_LIST`、`HUD_PLAYERS_INDICATOR`、猎手的 `L_HunterPlayers` 以及可能的击杀/结果界面逐一确认是否复用同一玩家条目；未复用的视图需在各自显示更新点调用同一映射服务。
5. 保留 EOS 原名作为模组调试/身份数据；重写仅作用于玩家名称文本。断开会话时清空本地映射。

若希望排序在整局中稳定，应按玩家首次进入本局的顺序分配编号并保留到离开；不要依赖 EOS 快照数组下标，因为其顺序不保证等于游戏显示顺序。

## 结论与未完成项

目前已确认“玩家条目名称更新”和“猎手列表/HUD 组件”是不同层次的路径。推荐方案是为两边提供同一套本地阵营编号映射，在最终 UI 文本消费点应用名称；不要修改 EOS 昵称或网络复制字段。

尚未确认：

- `0x18079E320` 的最终 `IUIText` 文本写入指令/调用点及稳定 hook 签名。
- `0x1808030F0` 是否只初始化猎手列表，及其运行时刷新函数。
- 击杀提示、比分/结算页是否另有独立名称路径。
- 当前 EOS `TEAM_l` / `ZOMBIE_b` 字段是否与运行时阵营状态完全一致。

这些项目需要继续检查上述函数的全部调用者、关键虚表槽和运行时会话对象；不能从本次字符串 xref 单独推断。
